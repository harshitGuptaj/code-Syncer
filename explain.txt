WHAT IS CODE SYNC?
------------------
Code Sync is a real-time collaborative code editor. Multiple users can join
a room using a unique Room ID and code together simultaneously. Changes made
by one user are instantly visible to all others in the same room.


HOW IT WORKS
------------
The project has two main parts:

1. CLIENT (Frontend) - Built with React + TypeScript
   - Runs on: http://localhost:5173
   - What it does: Provides the user interface for coding and managing files.

2. SERVER (Backend) - Built with Node.js + Express + Socket.io
   - Runs on: http://localhost:3000
   - What it does: Handles real-time communication between users using
     WebSockets (Socket.io). It syncs code and file changes across all
     connected users.


USER FLOW
---------
1. User opens the app → sees the Home Page with a join form
2. User enters a Room ID and Username → clicks "Join"
3. Server creates/joins the room → redirects user to the Editor Page
4. Multiple users can join the same room using the same Room ID
5. All changes (code, files) sync in real-time

---------- SERVER ----------

FILE: server/src/server.ts
WHAT IT DOES: The entire backend server
HOW IT WORKS:
  - Creates Express server with CORS enabled
  - Creates Socket.io server for real-time communication
  - Maintains userSocketMap[] array (all connected users)
  
  HELPER FUNCTIONS:
  - getUsersInRoom(roomId)      → returns all users in a room
  - getRoomId(socketId)         → finds room ID by socket ID
  - getUserBySocketId(socketId) → finds user by socket ID
  
  SOCKET EVENT HANDLERS:
  - JOIN_REQUEST        → Validates username, adds user to room
  - disconnecting       → Removes user, notifies others
  - FILE_CREATED        → Broadcasts new file to room
  - FILE_UPDATED       → Broadcasts code changes to room
  - FILE_RENAMED       → Broadcasts file rename to room
  - FILE_DELETED       → Broadcasts file deletion to room
  - DIRECTORY_CREATED → Broadcasts new folder to room
  - DIRECTORY_UPDATED  → Broadcasts folder changes to room
  - DIRECTORY_RENAMED  → Broadcasts folder rename to room
  - DIRECTORY_DELETED → Broadcasts folder deletion to room
  - SEND_MESSAGE       → Broadcasts chat message to room
  - TYPING_START     → Broadcasts typing status with cursor position
  - TYPING_PAUSE    → Broadcasts typing stopped
  - CURSOR_MOVE     → Broadcasts cursor position change
  - USER_ONLINE      → Broadcasts user came back online
  - USER_OFFLINE    → Broadcasts user went offline

CONNECTS TO: All frontend socket events via Socket.io

SECTION 1: BASIC QUESTIONS
--------------------------

Q1: How do users join a room in Code Sync?
A1: Users enter a Room ID and Username on the home page and click "Join".
    The server validates the username (must be unique in that room) and
    adds the user to the room using Socket.io.


Q2: What is Socket.io and why is it used?
A2: Socket.io is a WebSocket library that enables real-time bidirectional
    communication. It handles:
    - Real-time code syncing between users
    - Connection management
    - Fallback to HTTP long-polling if WebSocket fails
    - Event-based communication (join, type, cursor move, etc.)


Q3: How is real-time code syncing implemented?
A3: When a user types in the code editor:
    1. CodeMirror emits a 'change' event
    2. The client emits 'file-updated' socket event to server
    3. Server broadcasts to all other users in the room
    4. Other clients receive and update their editors


Q4: How do you handle multiple users working on the same file?
A4: Each user has their own file state. When User A types, their changes are
    broadcast immediately. Other users see the changes as they happen.


================================================================================
SECTION 2: KEY CONCEPT - MULTIPLE USERS ON SAME LINE
================================================================================

Q5: What happens when two or more users work on the SAME CODE at the SAME LINE?

A5: This is a CRITICAL question for collaborative editing. Here's how it works:

    MECHANISM:
    - When User A types at line 5, their full document content is sent to server
    - Server broadcasts to all users in the room
    - Each user's editor is updated with the new content
    
    WHAT HAPPENS:
    - The user who types FIRST - their changes are preserved
    - The user who types SECOND - their changes will be OVERWRITTEN by the broadcast
    - Last write wins - whoever types last gets their changes shown
    
    LIMITATION:
    - There is NO operational transformation (OT) or CRDT implementation
    - This is a KNOWN LIMITATION of the current implementation
    - In production, you would use OT (Operational Transformation) or CRDT 
      (Conflict-free Replicated Data Type) to handle conflicts
    
    CURRENT BEHAVIOR:
    - User A types: "function hello() {"
    - User B types: "function world() {"
    - Whichever message arrives last at the server wins
    - Both users will see the same final content


Q6: How do you handle cursor position sync for multiple users?
A6: The server tracks each user's cursor position:
    - When user starts typing: emits TYPING_START with cursorPosition
    - When user moves cursor: emits CURSOR_MOVE event
    - Server broadcasts to all users in the room
    - Clients render colored cursors showing other users' positions


Q7: What is the difference between TYPING_START and CURSOR_MOVE events?
A7:
    - TYPING_START: User is actively typing (shows green typing indicator)
    - CURSOR_MOVE: User just moved cursor without typing (no typing indicator)

Q12: What socket events are used in the server?
A12: The server handles these main events:
    - JOIN_REQUEST: User wants to join a room
    - FILE_CREATED, FILE_UPDATED, FILE_RENAMED, FILE_DELETED
    - DIRECTORY_CREATED, DIRECTORY_UPDATED, DIRECTORY_RENAMED, DIRECTORY_DELETED

Q13: How does the server track users?
A13: The server maintains a userSocketMap array:
    interface User {
        username: string
        roomId: string
        status: "online" | "offline"
        cursorPosition: number
        typing: boolean
        socketId: string
        currentFile: string | null
    }


Q14: What happens when a user disconnects?
A14: On disconnect:
    - Server removes user from userSocketMap
    - Notifies all users in the room via USER_DISCONNECTED event
    - User is removed from the room (socket.leave)

SECTION 6: ADVANCED QUESTIONS
================================================================================

Q17: What are the limitations of the current implementation?
A17:
    1. No conflict resolution (last write wins)
    2. No operational transformation (OT)
    3. No CRDT implementation
    4. No user authentication
    5. No room password protection
    6. Code execution depends on external API (Piston/Judge0)


Q18: How would you improve conflict handling for concurrent editing?
A18: Two main approaches:
    
    A) Operational Transformation (OT):
       - Transform operations so they can be applied in any order
       - Used by Google Docs, Etherpad
       - Requires central server to manage transform history
       
    B) CRDT (Conflict-free Replicated Data Type):
       - Data structure that automatically resolves conflicts
       - Yjs library provides CRDT for text editing
       - Can work in peer-to-peer mode
       - More complex but more robust


Q19: What security measures are implemented?
A19:
    - CORS enabled but set to "*" (should be restricted in production)
    - No authentication system
    - No input sanitization for code execution
    - Room IDs are not password protected
    
    RECOMMENDATIONS FOR PRODUCTION:
    - Add user authentication (JWT)
    - Implement rate limiting
    - Restrict CORS to specific domains
    - Sanitize inputs
    - Add room password protection


Q20: How does the drawing/whiteboard feature work?
A20:
    - Canvas-based drawing
    - User clicks "Draw" to enable drawing mode
    - Drawing data synced via DRAWING_UPDATE events
    - Other users see drawings in real-time

================================================================================
  ANSWERS TO THE KEY QUESTION - WHEN TWO USERS WORK ON SAME LINE
================================================================================

QUESTION: When two or more users work on the same code at the same line,
what happens?

DETAILED ANSWER:

In the current implementation of Code Sync:

1. USER TYPE SEQUENCE:
   - User A starts typing at position 100
   - User B also starts typing at position 100
   
2. SERVER HANDLING:
   - Server receives both updates via FILE_UPDATED events
   - No transformation is applied
   - Last update overwrites previous

3. RESULT:
   - Whichever user's update reaches the server LAST wins
   - Both users see the same final code
   - The first user's changes are LOST

4. EXAMPLE:
   Timeline:
   
   User A: types "abc" ---------> sent to server
   User B: types "xyz" ----> sent to server (arrives first)
   
   Result: Both users see "xyz"
   User A's "abc" is LOST - overwritten by User B's changes

5. WHY THIS HAPPENS:
   - We don't use Operational Transformation (OT)
   - We don't use CRDT (Conflict-free Replicated Data Type)
   - Simple broadcast - last write wins
   - No conflict resolution algorithm implemented

6. WHAT USERS SEE:
   - User types something, but suddenly their code DISAPPEARS
   - Other user's code overwrites their changes
   - Cursor might jump to unexpected position
   - No error message - just unexpected behavior

7. LIMITATION:
   - This is NOT suitable for production use
   - For production: use Yjs with CodeMirror or implement OT

8. HOW TO FIX:
   - Integrate Yjs (CRDT library) with CodeMirror:
     npm install yjs y-codemirror
   - Or use operational-transform library
   - Or implement server-side operation ordering
